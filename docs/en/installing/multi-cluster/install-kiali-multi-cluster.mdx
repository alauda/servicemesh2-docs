# Installing Kiali in a multi-cluster mesh

A single Alauda Build of Kiali instance can observe an entire multi-cluster mesh. You deploy the Kiali server on one cluster, then grant it read access to every other cluster in the mesh. The remaining clusters only need the resources that the Kiali server authenticates with — no Kiali server runs there.

:::note
In this procedure, `CLUSTER1` is the **East** cluster and hosts the Kiali server, and `CLUSTER2` is the **West** cluster and contributes only remote cluster resources.

You can adapt these instructions for a mesh spanning more than two clusters by repeating the **West** steps on each additional cluster.
:::

## Prerequisites

- You have deployed a multi-cluster mesh by following either [Installing a multi-primary multi-network mesh](./install-multi-primary-multi-network.mdx) or [Installing a primary-remote multi-network mesh](./install-primary-remote-multi-network.mdx).
- You have installed the Alauda Build of Kiali Operator on **every** cluster in the mesh, including the clusters where no Kiali server is deployed. See [Installing Alauda Build of Kiali](../../integration/observability/kiali.mdx).
- You have configured metrics collection on **every** cluster in the mesh by following [Configuring Monitoring with Service Mesh](../../integration/observability/metrics-and-mesh.mdx), with the `mesh_id` relabeling in the `PodMonitor` object and the `mesh_id` tag override in the `Telemetry` resource both enabled. Kiali distinguishes clusters by the `source_cluster` and `destination_cluster` labels that Istio adds to these metrics.
- Kiali requires a single endpoint that returns metrics for all clusters in the mesh. In Alauda Container Platform the monitoring store already spans clusters, so every cluster reports the same address. Read it with the following command:

  ```bash
  kubectl get feature monitoring -o jsonpath='{.spec.accessInfo.database.address}'
  ```

  The address is the value you set in `spec.external_services.prometheus.url` of the `Kiali` resource. You do not need to federate metrics stores yourself.

- The Kiali deployment namespace and instance name are identical on all clusters. If you change either default, apply the same value to `spec.deployment.namespace` and `spec.deployment.instance_name` in the `Kiali` resource on every cluster. This procedure uses the defaults, `istio-system` and `kiali`.
- You know the `meshID` and the per-cluster `multiCluster.clusterName` values that you set in the `Istio` resource of each cluster. This procedure uses `mesh1`, `cluster1`, and `cluster2`.
- You have `kubectl` configured with a context for each cluster. The following environment variables are used throughout:

  ```bash
  export CTX_CLUSTER1=<your cluster1 context>
  export CTX_CLUSTER2=<your cluster2 context>
  ```

## Procedure \{#procedure}

<Steps>
  ### Deploy the Kiali server on the **East** cluster

  Follow [Configuring Monitoring with Kiali](../../integration/observability/kiali.mdx#configuring-monitoring-with-kiali) to create the `Kiali` resource on the **East** cluster, then add the multi-cluster specific setting shown below.

  Because the monitoring store also holds metrics produced outside the mesh, restrict Kiali to this mesh by setting a query scope:

  ```yaml title="kiali-query-scope.yaml"
  spec:
    external_services:
      prometheus:
        query_scope:
          mesh_id: mesh1  # [!code callout]
  ```

  <Callouts>
    1. Must match `.spec.values.global.meshID` in the `Istio` resource of every cluster in the mesh. Kiali appends this label to every metrics query, so series that do not carry it are ignored.
  </Callouts>

  Apply the setting by running the following command:

  ```bash
  kubectl --context "${CTX_CLUSTER1}" -n istio-system patch kiali kiali \
    --type merge -p "$(cat kiali-query-scope.yaml)"
  ```

  ### Create a `Kiali` resource on the **West** cluster that produces only remote cluster resources

  Create a YAML file named `kiali-remote.yaml` with the following content:

  ```yaml title="kiali-remote.yaml"
  apiVersion: kiali.io/v1alpha1
  kind: Kiali
  metadata:
    name: kiali
    namespace: istio-system  # [!code callout]
  spec:
    deployment:
      instance_name: kiali  # [!code callout]
      remote_cluster_resources_only: true  # [!code callout]
  ```

  <Callouts>
    1. Must be the same namespace that holds the Kiali server on the **East** cluster.
    2. Must be the same instance name that the Kiali server uses on the **East** cluster. The Operator derives the service account name from it, so a mismatch makes the server unable to authenticate.
    3. Instructs the Operator to create only the resources that the remote Kiali server needs — a `kiali-service-account` service account and a `kiali-viewer` cluster role with its binding. No Kiali server, service, or ingress is created on this cluster.
  </Callouts>

  Apply the YAML file on the **West** cluster by running the following command:

  ```bash
  kubectl --context "${CTX_CLUSTER2}" apply -f kiali-remote.yaml
  ```

  Wait for the resource to reconcile:

  ```bash
  kubectl --context "${CTX_CLUSTER2}" wait --for=condition=Successful \
    kialis/kiali -n istio-system --timeout=3m
  ```

  ### Create a long-lived service account token on the **West** cluster

  The Kiali server authenticates to remote clusters with a service account token that does not expire. Kubernetes no longer generates such a token automatically, so create it explicitly.

  Create a YAML file named `kiali-svc-account-token.yaml` with the following content:

  ```yaml title="kiali-svc-account-token.yaml"
  apiVersion: v1
  kind: Secret
  metadata:
    name: kiali-service-account
    namespace: istio-system
    annotations:
      kubernetes.io/service-account.name: kiali-service-account  # [!code callout]
  type: kubernetes.io/service-account-token  # [!code callout]
  ```

  <Callouts>
    1. Binds the token to the service account that the previous step created. For a non-default instance name, use `<instance_name>-service-account`.
    2. Makes the token controller populate the `token` key of this secret.
  </Callouts>

  Apply the YAML file on the **West** cluster by running the following command:

  ```bash
  kubectl --context "${CTX_CLUSTER2}" apply -f kiali-svc-account-token.yaml
  ```

  :::warning
  Do not skip this step. Without this secret the next steps cannot read a token for the remote cluster, and generating the remote cluster secret fails.
  :::

  ### Obtain a `kubeconfig` for the **West** cluster that uses the platform API endpoint

  Download the `kubeconfig` of the **West** cluster from the Alauda Container Platform web console, or retrieve it from the platform API:

  ```bash
  curl -sS -H "Authorization: Bearer <your-platform-api-token>" \
    "<platform-url>/auth/v1/clusters/<west-cluster-name>/kubeconfig"
  ```

  The downloaded `kubeconfig` contains two contexts. Use the `proxy-connect` context, which is the default, and whose server address has the following form:

  ```text
  https://<platform-url>/kubernetes/<west-cluster-name>
  ```

  :::danger
  The remote cluster secret must address the remote cluster through this platform endpoint, not through the cluster API server address used by the `direct-connect` context.

  The platform endpoint accepts both the Kiali service account token and the platform tokens of logged-in users, whereas a cluster API server accepts only the former. With a `direct-connect` address, the Kiali server still reports the cluster as accessible, but every user-scoped request fails and the remote cluster contributes no namespaces to the Kiali console. For the symptoms, see [Troubleshooting](#troubleshooting).
  :::

  Add the `proxy-connect` context to the `kubeconfig` that also holds your **East** cluster context, so that a single `kubeconfig` can reach both clusters. This procedure refers to it as `${CTX_CLUSTER2_PROXY}`.

  ### Create a remote cluster secret on the **East** cluster

  The remote cluster secret holds a `kubeconfig` that lets the Kiali server on the **East** cluster read the **West** cluster. Generate it with the `kiali-prepare-remote-cluster.sh` script.

  Download the script and make it executable by running the following commands:

  ```bash
  curl -L -o kiali-prepare-remote-cluster.sh \
    https://raw.githubusercontent.com/kiali/kiali/master/hack/istio/multicluster/kiali-prepare-remote-cluster.sh
  chmod +x kiali-prepare-remote-cluster.sh
  ```

  Run the script by using the following command:

  ```bash
  ./kiali-prepare-remote-cluster.sh \
    --kiali-cluster-context "${CTX_CLUSTER1}" \
    --remote-cluster-context "${CTX_CLUSTER2_PROXY}" \
    --remote-cluster-name cluster2 \
    --remote-cluster-namespace istio-system \
    --kiali-resource-name kiali-service-account \
    --process-remote-resources false \
    --process-kiali-secret true \
    --view-only false
  ```

  The options have the following effects:

  - `--remote-cluster-name`: the name that Istio uses for the remote cluster, taken from `.spec.values.global.multiCluster.clusterName`. Always set it explicitly, because the name the script would otherwise derive from the context may contain characters that are invalid in a secret key.
  - `--remote-cluster-namespace`: the namespace on the remote cluster that holds the service account and its token.
  - `--kiali-resource-name`: the service account that the Operator created in step 2.
  - `--process-remote-resources false`: skips creating the service account and roles, because the `Kiali` resource already manages them.
  - `--process-kiali-secret true`: creates the secret in the Kiali deployment namespace on the **East** cluster.
  - `--view-only false`: grants Kiali write access to the remote cluster. Set it to `true` to restrict Kiali to read-only operations on that cluster.

  On success the script reports the server address it read from the context and the name of the secret it created:

  ```text
  INFO: remote_cluster_server_url=https://<platform-url>/kubernetes/<west-cluster-name>
  secret/kiali-remote-cluster-secret-cluster2 created
  ```

  :::tip
  Use the `--help` option to display all the options that the script supports, including `--delete true` for removing what it created.
  :::

  <details>
    <summary>Creating the remote cluster secret without the script (click to expand)</summary>

    In an environment without access to GitHub, create the secret manually. Read the token and the platform certificate authority first:

    ```bash
    export REMOTE_TOKEN=$(kubectl --context "${CTX_CLUSTER2}" -n istio-system \
      get secret kiali-service-account -o jsonpath='{.data.token}' | base64 -d)

    # Base64-encoded certificate authority of the platform. Copy it from the
    # certificate-authority-data field of the proxy-connect cluster entry in the
    # kubeconfig that you downloaded in the previous step.
    export PLATFORM_CA=<platform-ca>
    ```

    Then create a YAML file named `kiali-remote-secret.yaml` with the following content:

    ```yaml title="kiali-remote-secret.yaml"
    apiVersion: v1
    kind: Secret
    metadata:
      name: kiali-remote-cluster-secret-cluster2
      namespace: istio-system
      labels:
        kiali.io/multiCluster: "true"  # [!code callout]
    stringData:
      cluster2: |  # [!code callout]
        apiVersion: v1
        kind: Config
        preferences: {}
        current-context: cluster2
        contexts:
        - name: cluster2
          context:
            cluster: cluster2
            user: cluster2
        users:
        - name: cluster2
          user:
            token: ${REMOTE_TOKEN}
        clusters:
        - name: cluster2
          cluster:
            server: https://<platform-url>/kubernetes/<west-cluster-name>  # [!code callout]
            certificate-authority-data: ${PLATFORM_CA}  # [!code callout]
    ```

    <Callouts>
      1. Makes the Operator detect the secret automatically. See [Registering remote cluster secrets](#registering-remote-cluster-secrets).
      2. The key must be the name that Istio uses for the remote cluster.
      3. The platform endpoint of the remote cluster, as described in step 4.
      4. The base64-encoded certificate authority of the platform, taken from the `certificate-authority-data` field of the downloaded `kubeconfig`.
    </Callouts>

    Render the manifest and apply it on the **East** cluster by running the following command:

    ```bash
    envsubst < kiali-remote-secret.yaml | kubectl --context "${CTX_CLUSTER1}" apply -f -
    ```
  </details>

  ### Trigger reconciliation of the Kiali server

  The Operator mounts remote cluster secrets into the Kiali server pod when it reconciles the `Kiali` resource. Annotate the resource to start a reconciliation:

  ```bash
  kubectl --context "${CTX_CLUSTER1}" annotate kiali kiali -n istio-system \
    --overwrite kiali.io/reconcile="$(date)"
  ```

  Wait for the resource and the server to become ready by running the following commands:

  ```bash
  kubectl --context "${CTX_CLUSTER1}" wait --for=condition=Successful \
    kialis/kiali -n istio-system --timeout=3m
  kubectl --context "${CTX_CLUSTER1}" rollout status deployment/kiali -n istio-system
  ```

  ### Log in to the Kiali console

  Open the Kiali console of the **East** cluster at `<platform-url>/clusters/<east-cluster-name>/kiali`.

  :::note
  A single login covers every cluster in the mesh. Because the remote cluster secrets address the clusters through the platform API endpoint, the platform authorizes your account on all of them, and you do not need to log in to each cluster separately.
  :::
</Steps>

## Registering remote cluster secrets \{#registering-remote-cluster-secrets}

The Kiali Operator can learn about remote cluster secrets in three ways. Choose one.

**Label based auto-detection**

This is the default, and it is what the preceding procedure relies on. The Operator mounts every secret in the Kiali deployment namespace that carries the `kiali.io/multiCluster=true` label. The relevant defaults are the following:

```yaml
spec:
  clustering:
    autodetect_secrets:
      enabled: true
      label: kiali.io/multiCluster=true
```

**Explicit declaration**

Set `autodetect_secrets.enabled` to `false` and name each secret in the `Kiali` resource:

```yaml
spec:
  clustering:
    autodetect_secrets:
      enabled: false
    clusters:
    - name: cluster2
      secret_name: kiali-remote-cluster-secret-cluster2
```

**One combined secret**

Place a `kubeconfig` for every remote cluster in a single secret named `kiali-multi-cluster-secret`, each under its own key in `stringData` where the key is the cluster name. Add the `kiali.io/kiali-multi-cluster-secret: "true"` label so that the Operator restarts the Kiali server automatically whenever the secret changes:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: kiali-multi-cluster-secret
  namespace: istio-system
  labels:
    kiali.io/kiali-multi-cluster-secret: "true"
stringData:
  cluster2: |
    # kubeconfig for cluster2
  cluster3: |
    # kubeconfig for cluster3
```

:::warning
Never apply the `kiali.io/kiali-multi-cluster-secret: "true"` label to a secret with a different name. The Operator has no permission to read such a secret and errors occur.

If several Kiali servers share a namespace, they all have to use the combined secret. To let each server reach a different set of clusters, do not use the combined secret.
:::

## Adding an inaccessible cluster

If you prefer a separate Kiali server per cluster, or you cannot grant one Kiali server access to the other clusters, declare the other clusters without a secret. Each Kiali console then renders links to the console that observes the remote cluster, instead of the remote data itself.

On the **East** cluster, describe the **West** cluster as follows:

```yaml
spec:
  clustering:
    clusters:
    - name: cluster2  # [!code callout]
    kiali_urls:
    - cluster_name: cluster2
      instance_name: kiali  # [!code callout]
      namespace: istio-system
      url: https://<platform-url>/clusters/<west-cluster-name>/kiali  # [!code callout]
```

<Callouts>
  1. Omitting `secret_name` marks the cluster as inaccessible.
  2. The instance name and namespace of the Kiali server that observes that cluster.
  3. The address that the Kiali console links to. It must be reachable from the browser.
</Callouts>

Apply the mirror-image configuration on the **West** cluster so that both consoles link to each other.

## Removing a cluster from Kiali

**Procedure**

1. Delete the remote cluster secret from the Kiali deployment namespace on the cluster that hosts the Kiali server:

   ```bash
   kubectl --context "${CTX_CLUSTER1}" -n istio-system \
     delete secret kiali-remote-cluster-secret-cluster2
   ```

   <Directive type="note">

   If you created the secret with `kiali-prepare-remote-cluster.sh`, run the script again with the same options plus `--delete true`.

   </Directive>

2. Remove the service account and roles from the remote cluster by deleting its `Kiali` resource:

   ```bash
   kubectl --context "${CTX_CLUSTER2}" -n istio-system delete kiali kiali
   ```

3. Make the Kiali server stop looking for the deleted secret:

   - With label based auto-detection, trigger a reconciliation:

     ```bash
     kubectl --context "${CTX_CLUSTER1}" annotate kiali kiali -n istio-system \
       --overwrite kiali.io/reconcile="$(date)"
     ```

   - With explicit declaration, remove the corresponding entry from `spec.clustering.clusters`.
   - With one combined secret, no action is needed. The Operator notices the change and redeploys the Kiali server.

## Verification

1. Confirm that the Kiali server discovered every cluster by running the following command:

   ```bash
   kubectl --context "${CTX_CLUSTER1}" logs -n istio-system deployment/kiali | grep "Discovered cluster"
   ```

   Each cluster in the mesh appears with `Accessible=true`, and exactly one of them with `IsKialiHome=true`:

   ```text
   INF Discovered cluster: Name=[cluster1], Accessible=true, IsKialiHome=true, ApiEndpoint=[https://100.4.0.1:443], SecretName=[]
   INF Discovered cluster: Name=[cluster2], Accessible=true, IsKialiHome=false, ApiEndpoint=[https://<platform-url>/kubernetes/<west-cluster-name>], SecretName=[kiali-remote-cluster-secret-cluster2]
   ```

2. In the Kiali console, navigate to **Overview** and confirm that namespaces from every cluster are listed. The cluster name is shown on each namespace card.

3. Navigate to **Mesh** and confirm that every cluster appears with its own control plane and data plane node.

4. Navigate to **Traffic Graph**, select a namespace that exists on more than one cluster, and confirm that the graph draws the clusters separately with edges between them. Enable **Display** > **Cluster Boxes** to group the nodes by cluster.

## Troubleshooting \{#troubleshooting}

**The remote cluster is reported as accessible, but its namespaces are missing from the console**

The Kiali server log shows the following entries:

```text
INF Discovered cluster: Name=[cluster2], Accessible=true, IsKialiHome=false, ...
INF Error fetching Namespaces for cluster [cluster2]: Unauthorized
WRN Error checking Istio API configuration: the server has asked for the client to provide credentials
```

The remote cluster secret addresses the cluster API server directly, so the service account token of Kiali works but the platform token of the logged-in user is rejected. Change the `server` field of the `kubeconfig` in the secret to the platform endpoint, `https://<platform-url>/kubernetes/<cluster-name>`, together with the matching certificate authority, and trigger a reconciliation. See step 4 of the [Procedure](#procedure).

**Generating the remote cluster secret never completes**

The script repeats the following message and then fails:

```text
INFO: Waiting for the remote cluster SA secret token to be created...
ERROR: There is no token assigned yet to the remote cluster SA secret [kiali-service-account] found in remote cluster namespace [istio-system].
```

The long-lived service account token secret is missing on the remote cluster. Complete step 3 of the [Procedure](#procedure), then run the script again.

**Graphs are empty although the clusters are accessible**

Confirm that the metrics of all clusters carry the `mesh_id` label that `spec.external_services.prometheus.query_scope` filters on:

```bash
curl -sS -u "<monitoring-user>:<monitoring-password>" \
  --data-urlencode 'query=count(istio_requests_total{mesh_id="mesh1"}) by (source_cluster, destination_cluster)' \
  "<monitoring-address>/api/v1/query"
```

The result must contain one series per cluster pair that exchanges traffic. If it is empty, either the `mesh_id` relabeling is missing from the `PodMonitor` object of a cluster, or the value does not match the `meshID` of the `Istio` resource. See [Configuring Monitoring with Service Mesh](../../integration/observability/metrics-and-mesh.mdx).
